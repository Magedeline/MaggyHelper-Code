# Desolo Zantas Discussions Plan

This file is a starter structure for GitHub Discussions so the repo has clear channels instead of routing everything into issues or PR comments.

## Goals

- Separate design talk from implementation work
- Give contributors a place to ask setup and mapping questions
- Keep bug reports and concrete tasks in Issues
- Preserve decisions that are otherwise lost in chat or PR threads

## Recommended Categories

### Announcements

Use for maintainer-only updates.

- Release planning
- Milestone changes
- Big pipeline or ruleset updates
- Contributor callouts or asset review deadlines

### General

Use for broad repo conversation that does not yet belong in an Issue.

- Project direction
- Chapter planning
- Scope discussions
- Coordination across mapping, code, and writing

### Ideas

Use for proposals before they become implementation tasks.

- New chapter concepts
- Boss redesign ideas
- Kirby mechanic extensions
- Optional mode or bonus content proposals

### Q&A

Use for answerable contributor questions.

- Build setup
- Loenn usage
- Dependency confusion
- Where systems live in the codebase
- How to add or test content safely

### Show and Tell

Use for WIP previews and feedback requests.

- Room mockups
- Sprite tests
- Cutscene drafts
- Music previews

### Playtesting Reports

Use for structured player feedback that is not yet a formal bug.

- Difficulty spikes
- Clarity issues
- Pacing concerns
- Soft progression confusion

When a report is confirmed actionable, convert it into an Issue.

### Wiki and Docs

Use for documentation gaps and planned wiki improvements.

- Missing setup docs
- Entity reference pages needed
- Terminology cleanup
- Contributor onboarding friction

## Category-to-Tracker Rules

- Use Discussions for exploration, coordination, and open-ended design.
- Use Issues for confirmed bugs, concrete tasks, and follow-up work.
- Use Pull Requests for implementation and review only.

## Suggested Pinned Discussions

1. Start Here: How to contribute to Desolo Zantas
2. Mapping workflow for chapters and sub-maps
3. Bug triage policy: when to open an Issue instead
4. Asset credit and sourcing rules
5. Weekly coordination thread

## Suggested Discussion Templates

### Idea Template

Title format:

`Idea: short proposal`

Body:

- Problem or opportunity
- Proposed change
- Affected chapter or system
- Risks or dependencies
- What feedback is needed

### Q&A Template

Title format:

`Question: short topic`

Body:

- What you are trying to do
- What file, map, or system is involved
- What you already checked
- Exact blocker or confusion

### Playtest Report Template

Title format:

`Playtest: chapter/area summary`

Body:

- Chapter, side, and room
- Expected behavior
- Observed behavior
- Repro steps if consistent
- Severity
- Whether this should become an Issue

## Suggested Maintainer Workflow

1. Check new Discussions during the weekly quality review.
2. Label actionable outcomes in the discussion body or first reply.
3. Convert confirmed bugs and tasks into Issues.
4. Close stale idea threads only after summarizing the decision.
5. Move durable answers into the Wiki when the same question repeats.

## Moderation Rules

- Keep feature requests separate from bug reports.
- Keep design debates concrete and chapter-specific where possible.
- Redirect implementation details from Discussions into PRs once work starts.
- Do not use Discussions as a substitute for review approval.

## Launch Checklist

1. Enable Discussions in repository settings.
2. Create the categories listed above.
3. Pin the starter threads.
4. Link the wiki and contributing guidance from the pinned Start Here post.
5. Add a short note to the README once Discussions are live.
